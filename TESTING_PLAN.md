# План тестирования: PostgreSQL и миграции

## Обзор

Этап покрывает конфигурацию таймаутов базы данных, подключение через pgxpool с ping, прогон миграций goose из встроенной FS и закрытие пула через lifecycle.

## Зависимости

- Юнит-тесты внешних сервисов не требуют: недоступность базы моделируется адресом `127.0.0.1:1`, который отказывает в подключении мгновенно.
- Цикл миграций требует реальный PostgreSQL и запускается только при заданном `TEST_DATABASE_URL`, иначе тест пропускается.
- Все тесты, работающие с базой, живут в одном пакете `internal/repository/postgres`, поэтому `go test ./...` не гоняет миграции из нескольких пакетов параллельно по одной базе.

## Тест-кейсы

### Config

- [x] Default `DATABASE_CONNECT_TIMEOUT=15s` и `DATABASE_MIGRATE_TIMEOUT=3m`.
- [x] Пользовательские значения обоих таймаутов.
- [x] Нулевое, отрицательное и некорректное значение каждого таймаута.
- [x] Ошибка не раскрывает переданное значение.

### postgres

- [x] Provider читает встроенную FS и находит миграции (без базы, `sql.Open` ленивый).
- [x] Недоступная база даёт `ErrConnect` в пределах настроенного таймаута.
- [x] Некорректные параметры подключения дают `ErrConnect`.
- [x] Ни ошибка, ни логи не содержат пароль из DSN.
- [x] Неизвестная команда даёт `ErrCommand`, а не `ErrMigrate`.
- [x] Цикл up → status → down → up на чистой базе, с проверкой наличия и отсутствия всех шести таблиц.
- [x] Миграция ждёт session advisory lock: пока лок удерживается извне, `Migrate` возвращает `ErrMigrate` по таймауту и не создаёт ни одной таблицы, а после освобождения проходит.

Тест на лок проверен на отрицательном контроле: при удалении `goose.WithSessionLocker` он падает. Попытка воспроизвести гонку четырьмя параллельными горутинами оказалась бесполезной — она проходила и без лока, поэтому заменена на детерминированную проверку самой блокировки.

### Entry points

- [x] `api`, `worker` и `migrate` завершаются с кодом 1 и событием отказа подключения, когда база недоступна.
- [x] Некорректная конфигурация по-прежнему даёт код 1 и безопасный stderr.
- [x] Логи отказа не содержат test secrets, включая пароль из DSN.

## Покрытие

Цель: покрыть ветви `Connect`, `Migrate` и `InitDB`, новые config validation cases и путь отказа во всех трёх entry points.

Ручной проверкой закрыто то, что автотесты не покрывают без базы: старт `api` с прогоном миграций, SIGTERM, закрытие пула задачей `postgres` и код выхода 0; то же для `worker` без миграций; `migrate up/status/down` и состав таблиц и индексов после `up`.

Отдельно проверен rolling deploy: три инстанции `api` и ручной `migrate up` запущены одновременно на пустой схеме. Миграцию применила ровно одна из них, остальные увидели отсутствие pending-миграций, все процессы завершились кодом 0, в `goose_db_version` нет дублей версий.
